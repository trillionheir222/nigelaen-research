Prismæon™

Making consequential compute operations explicit, bounded, and reviewable.

Prismæon is a governed adaptive-compute architecture for hardware-controlled and heterogeneous workloads, developed by Nigel Patch through Prismaeon Inc. It makes the boundary around an important operation more explicit: what was authorized, what executed, what completed, and what evidence supports acceptance.

The idea at a glance

A software request should not become an accepted result without explicit authority, completion, validation, and evidence.

Why build a governed
compute boundary?

In many systems, software helps request an operation, authorize it, interpret its completion, and record whether it succeeded. A fault or compromise in that environment can therefore affect both the action and the evidence used to judge it.

Prismæon explores a stricter division of responsibility. The host proposes work, while the control path checks authority and live state; the device accepts only bounded work; and completion is accepted only when state and evidence reconcile.

In plain language: the system is designed to ask not only “did something run?” but also “was it allowed, did the expected operation finish, can the result be checked, and can the system recover cleanly if those answers disagree?”

Operational model

Six stages separate a request
from an accepted result.

01

Proposal

The host presents a bounded operation through a defined protocol.

02

Authorization

Required authority and current device-state conditions are checked.

03

Execution

The FPGA accepts only a request that satisfies the governed boundary.

04

Completion

Submission and completion ordering remain tied to the operation.

05

Validation

The result and required evidence must reconcile.

06

Acceptance

Only a validated completion is accepted; mismatches stop fail-closed.

The purpose is not simply to move data faster. It is to make the operating boundary, completion criteria, and evidence model explicit enough to inspect and test.

What has been demonstrated
on the tested configuration.

The current evidence supports a physical reference implementation and bounded-operation claims. The figures below describe governed data-movement transactions in specific test campaigns, not general application throughput.

Sustained validation

22,071

accepted operations

Approximately 30 minutes, five payload sizes, queue depth one, with zero recorded retries, validation errors, lost commands, duplicate executions, or unexpected faults in the observed campaign.

Verified I/O

100

A separate physical-I/O functional-integration campaign recorded 100 accepted operations, 100 validated destinations, 200 verified writes, and 400 durability boundaries.

Recovery behavior

0/0

verified clean state

Recorded mismatch scenarios stopped without silent acceptance. Separate recovery procedures unloaded and reloaded the platform while preserving identity and returning it to a verified clean state.

Evidence boundary: these observations apply to the tested FPGA configuration, duration, queue depth, and payload population. They do not establish lifetime reliability, certification, broad workload performance, production readiness, power advantage, or commercial superiority.

Current direction

Move from a founder-built physical reference implementation to a reviewable evaluation platform.

What comes next.

The next stage is not presented as a foregone conclusion. It is an evidence program: package the reference implementation and host interface for controlled evaluation, test relevant external workloads, compare against matched baselines, measure overhead and resource behavior, and let those results determine the appropriate future hardware path.

  1. 01Package the reference implementation, runtime, evidence, and recovery tooling for controlled evaluation.
  2. 02Engage technically qualified reviewers and prospective evaluation partners.
  3. 03Characterize latency, throughput, resource overhead, and power where suitable measurement is available.
  4. 04Use the evidence—not the ambition—to decide what should be optimized, productized, or advanced toward future hardware.
